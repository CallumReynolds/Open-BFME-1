## Hypothesis and result

The retry tests whether return-type qualification, actual value-copy types, helper visibility, explicit output-parameter declarations or a different native temporary lifetime explain the unaccessed frame region before the receiver spill. Complete decoded calls support these representation alternatives; they do not support widening a value merely to reserve storage. Each trial records its hypothesis and refutation condition beside its source hash. An unchanged frame refutes that spelling; added stores, calls or saved registers refute its compatibility with the retail stream. No trial improves the original bank. This exhausts the supported experiments recorded here, not every possible C++ spelling.

The baseline is build/target-00077ce0-run9/01-original-bank.probe.log. Its JSON receipt records every differing offset and all fifteen relocation operands. Every operand aligns with the same complete decoded retail instruction field. The table below is generated from those bytes and instructions. ## Boundaries, fields and physical ABI

The target's complete extent is [0x00077CE0, 0x00077E33), bracketed by INT3 padding. Its sole return is `ret 4` at 0x00077E30. Every conditional branch and ordinary jump remains inside that extent and reaches the shared exit. There is no tail jump, indirect call, virtual call or exception registration in the target. The incoming ECX value is spilled and never read again. The incoming stack word at EBP+8 is passed by reference to the two searches. This establishes the physical call interface, without proving EA's owner, original parameter typedef or decoration.

The complete enclosing caller [0x00079060, 0x0007ACFA) contains the instruction-aligned call at 0x0007ACE2 through ILT 0x000423F7. It pushes 0x36 and passes the address of a zero-initialized byte in ECX. It consumes no return value before its epilogue (one observed call site). The fragment beginning at 0x0007AC77 is not used as an entry. The complete caller decode includes its catch continuations and returns. Its checked inventory reports no outgoing conditional branch or tail jump. No caller ledger row is changed.

The complete target, caller, singleton accessors, lookup and value helpers, and initial insertion chain are retained in build/target-00077ce0-run9/complete.decode.txt. The checked-<rva>.log files retain fresh checked-callee inventories. The final portion of that decode records each actual ILT jump, including the nested search and insertion routes. The additional node-header helper decodes are named below. No raw caller opcode hit or allocation size substitutes for those decodes.

Both singleton accessors return their static tree addresses in EAX without stack arguments. The wrappers at 0x000762B0 and 0x00075E80 forward an output pointer and key reference to the complete searches at 0x00072D70 and 0x00072730. Both search return paths write one node pointer through the output, return that output in EAX and use `ret 8`; their four-byte key comparisons are unsigned. The comparison helpers consume the two iterator node words; the target consumes AL. The dereference helper at 0x0006B540 returns node+0x10 with plain `ret`.

The complete copy helper at 0x0006C5E0 reads source+0 and source+4, writes destination+0 and destination+4, returns the destination receiver and uses `ret 4`. It assigns, adds or subtracts through the destination pointer, then writes the processed word. The first copied word is the key read by the map search. These observations establish the two-word key/pointer representation; they do not establish the original key typedef, local pair constness or arithmetic signedness.

The membership insertion chain through 0x00077C70, 0x00076E10, 0x00076190 and 0x00072C90 was decoded in full. Their raw instructions are in build/target-00077ce0-run9/header-helpers.decode.txt and rotations.decode.txt, with the measured offsets in header-field-offsets.json. This supports a scalar membership value independently of allocation size or a donor name. The complete 0x00077C70 helper ignores its incoming receiver and uses `ret 4`. Its zero-initialized receiver can be represented by an empty class with exactly the bank's output, so the inherited `bool flag` declaration is not independently proved. This target constructs no owning container and has no constructor unwind cleanup to recover.

The existing singleton sources, output-copy sources, native insertion sources and `ImageCollection::findImageByName` were read directly. The native tree iterator, tree search, set/map wrappers and pair constructors were also inspected. The retained record and receiver names are inherited diagnostic identifiers, not new EA identities. The owner remains address-derived.

## Verification and remaining blocker

The unmodified scoped verifier fails on the eight shape bytes and seven unresolved decorated calls in build/target-00077ce0-run9/final-bank.gate.log. Its string, constant, DIR32 and body checks pass. A final probe at the unchanged bank's actual path independently reproduces the same shape in final-bank.probe.log. CSV integrity, pin consistency and the unchanged bank's class gate pass in final-check-csv.log, pin-consistency.log and bank-class-gate.log in the same task folder. checks.json records the subprocess exits. The earlier 41-bank.gate.log is the shell-formatted initial check; the final log captures subprocess bytes directly. The provider-only diagnostic in 136-providers.gate.log passes both function byte comparisons but fails ownership of the singleton's existing DIR32 names. No pin, data-name rule or baseline is changed to clear that separate control. No shared header, shim or source ledger is changed, so a full gate is not required for this evidence-only result.

The frame region remains unexplained by a witnessed source lifetime. No experiment improves the saved bank, so it is not re-banked. The inherited marker assembly remains diagnostic and no clean C++ landing is claimed. Reopening requires an independently supported enclosing temporary or compiler mechanism that reserves the unaccessed region without moving the witnessed objects or adding instructions. Any future landing must also bind the decoded calls under defensible names, retaining address identities where the original owner is unknown. Unproved naming alone is not the reason for stopping. Exactly one blocked verdict records this run.
