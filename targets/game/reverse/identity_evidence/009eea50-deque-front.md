# Address-owned deque front helpers

The 31-byte body at 0x009EF930 and the 30-byte body at 0x009EEA50 both start after INT3 padding and end before INT3 padding. The former has a RET 4 fast path and a tail JMP at +0x1A to 0x009EF140; the latter has one internal unsigned conditional branch, one CALL to 0x009EE360 and a RET 4 at +0x1B. Every path and the tail target were decoded. Neither target has an exception handler. The extents and checked inventories are retained in build/donor-port/009ef930-extent.log, build/donor-port/009ef930-callees.log, build/donor-port/009eea50-extent.log and build/donor-port/009eea50-callees.log.

The Open BFME 2 donor is Code/Libraries/Source/WWVegas/WWLib/stlport_deque_int.cpp, at game.dat 0x006223F0 for push_front and 0x00621000 for reserve_map_at_front. Its int type is not transferred as evidence. BFME 1's complete 329-byte AddRequiredAssets caller at 0x009EFBF0 supplies independent pointer evidence: at +0x59 it loads a mapped entry pointer, dereferences the entry's +4 state word, updates that state and inserts the same pointer into one of the 0x28-byte queues at receiver+0x78. The fast path writes that single four-byte pointer; the slow path at +0xC5 passes the address of its pointer local to the actual 0x009EF140 helper. Raw complete caller evidence is build/donor-port/009efbf0-retail.log and build/donor-port/009efbf0-callees.log.

The complete 90-byte auxiliary at 0x009EF140 reads exactly one four-byte value from its reference argument, keeps that value across allocation, updates the start iterator's node, first, last and current fields, and writes exactly the saved value at the new current slot. Its only return removes the reference's four-byte stack slot. It has no hidden payload fields, value constructor, destructor or cleanup. Both the main allocation path and null-placement guard were reviewed. The 128-byte allocation is corroboration of the buffer span, not evidence that the payload is an int. The caller establishes that this value is a pointer, whose ultimate owner remains address-derived as Rva009EF0D0Element. See build/donor-port/009ef140-retail.log and build/donor-port/009ef140-callees.log.

The complete 367-byte map grower at 0x009EE360 reads a 32-bit added-node count and a byte Boolean, recenters or reallocates an array of four-byte node pointers, copies them with memmove, frees the old map when needed, updates the map and both iterator node/first/last fields, and returns with RET 8. All its internal conditional branches, allocation alternatives and return path were reviewed. It does not construct or destroy payload values. The reserve helper passes its own receiver unchanged in ECX, then pushes true and the 32-bit node count in that order. There are no virtual or adjusted-receiver calls. See build/donor-port/009ee360-retail.log and build/donor-port/009ee360-callees.log.

The previous reserve attempt was blocked by the GameResultsResponse name attached to 0x009EE360. The repository now also contains the independently evidenced deque<Rva009EF0D0Element*> pin for that exact body, along with the pointer-type push-front auxiliary pin at 0x009EF140. These current declarations are reused without introducing or changing a pin. The old GameResultsResponse ledger identity is not adopted, and this assignment does not correct that unrelated row. The new target identity remains opaque. Its source defines Rva009EEA50DequeView::reserve_front directly, using the native deque as a zero-offset implementation view. This introduces no receiver adjustment, new fields, ownership claim or claim about an engine inheritance relationship. It inlines the canonical reserve implementation and calls the existing pointer-type map-grower pin. The direct definition remains exact in build/donor-port/009eea50-direct-name-probe.log and needs no object-symbol alias.

The repository's native STLport deque header and its complete construction helper agree on four-byte elements, iterator fields and 0x28-byte container layout. Explicit instantiation with the address-derived pointer type produces exact 31-byte and 30-byte bodies in build/donor-port/009ef930-pointer-probe.log and build/donor-port/009eea50-pointer-probe.log. A wrong complete payload copy, a caller passing a nonpointer value, different receiver offsets, stack cleanup or tail target would refute this reconstruction.

The existing generated 5-byte row at 0x009EF94A is the tail instruction inside the complete 0x009EF930 body, rather than an independently padded entry. Landing that complete body must retire the interior row through the repository's supported boundary transaction; any refusal is retained in the raw add-match log rather than bypassed.

The complete push-front source is banked because add_match.py refuses the interior generated tail row. The ordinary addition and the boundary-replacement refusals are retained in build/donor-port/009ef930-add-match.log and build/donor-port/009ef930-boundary-add-match.log. The saved bank is targets/game/reverse/attempts/0x009ef930.cpp and independently remeasures at 1.0. Reopening requires a supported boundary correction that absorbs the generated row at 0x009EF94A; changing the C++ body is not justified by the measured bytes.
