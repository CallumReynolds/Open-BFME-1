# Address-owned float comparisons

The bodies at 0x009F2BE0 and 0x009F2C10 each occupy 34 bytes. Both follow INT3 padding, have two RET 8 paths ending at +0x22, and are followed by INT3 padding. Their conditional branches stay inside the complete bodies. Neither has a call, tail jump or exception handler. See build/donor-port/009f2be0-extent.log, build/donor-port/009f2c10-extent.log and their checked-callee logs.

Each body reads two four-byte reference arguments from the stack. ECX is unused, consistent with a stateless thiscall predicate. Each reference supplies a 32-bit floating-point value at +4. The first comparison returns true for ordered less-than, using TEST AH,5 and parity; the second returns true for ordered greater-than, using TEST AH,0x41 and nonzero. Both explicitly return either zero or one in EAX and remove eight bytes of argument storage. No adjustment or hidden result pointer is present.

The Open BFME 2 donors are Code/Libraries/Source/WWVegas/WWLib/stlport_push_heap_s4sortelem8.cpp at game.dat 0x00625880 and Code/Libraries/Source/WWVegas/WWLib/stlport_push_heap_s4sortelem8_desc.cpp at game.dat 0x006258B0. BFME 1 already has the complete corresponding operators beside its matched heap bodies. Their existing S4SortElem8 and comparator spellings are preserved. The complete operators are defined directly on Rva009F2BE0Predicate and Rva009F2C10Predicate, using the existing S4SortElem8 declaration and its unchanged field names. Their actual mangled symbols are the ledger names, and both direct definitions probe exact in the corresponding address-direct-name-probe.log files. The old comparator definitions remain intact and no object-symbol alias is used. The donor's comparator names are not introduced.

The comparator witnesses only the float at +4. It neither reads nor classifies the first four bytes of an element. The existing 96-byte heap bodies copy both four-byte words and advance through eight-byte elements. Those complete bodies establish the storage representation and reproduce the same floating comparison inline; they do not establish a semantic type for the first word, and no such identity is claimed. No allocation size or template name is used as independent type evidence.

The old claims at 0x009F2BF5 and 0x009F2C25 start at their respective predicates' true-result blocks (+0x15), immediately after its conditional branch. Each eight-byte range is contained in its complete predicate, with no padding or preceding return at its start. Each alias to IgnoreTwoArgumentsReturnOneThunk therefore describes shared interior instructions rather than an independently bounded function. The contained-claim corrections retire those aliases without editing their unrelated source.

A different complete decode, reference order, floating comparison, return width or stack cleanup would refute these reconstructions. An independent padded function entry at either interior address would refute the boundary correction. Raw probe and add-match outputs are retained under build/donor-port/ with the respective address prefixes.
